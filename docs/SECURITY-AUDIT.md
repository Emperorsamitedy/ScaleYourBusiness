# Security audit — 2026-10-17

A whole-codebase review of what was built through Phase 4 Session F (P4-16), on branch `security-hardening`. Four independent read-only reviews ran in parallel, one per area:

- identity, sessions and authorization, across all 41 API routes
- the public surface and server-side fetches
- secrets, connectors and the execution engine
- data exposure, injection and hardening

Every critical and high finding was then checked against the code by hand before it was fixed. Each fix has a test that names the attack it closes.

## Before you deploy this branch

1. **Email must work, or nobody can sign in.**
   - Production no longer shows sign-in links on screen. That fallback was the critical hole: anyone could sign in as anyone.
   - Set a working `RESEND_API_KEY` and an `EMAIL_FROM` on a domain verified in Resend. The default `onboarding@resend.dev` only delivers to the Resend account owner.
2. **Run the migrations:** `db:migrate` for 0039 (contact country, from PR #2) and 0040 (support reservations and the visitor hash). Then `db:seed` for bank 1.4.0, if PR #1's bank change isn't seeded yet.
3. **Everyone will sign in again once.**
   - The intake cookie is now signed. Anyone mid-intake on an unowned profile carries on without noticing, and their cookie is re-issued signed.
   - An owner whose session has expired is asked to sign in, because their profile no longer opens to its id alone. That is the fix, not a regression.
4. **Optional:** set `COOKIE_SECRET` to a fresh random value. Without it, the cookie and visitor-hash keys are derived from `CONNECTOR_KEY` by HKDF, so no new variable is required.

## Added 2026-10-26: footage upload and generated media (P3-52, P3-53)

## Added 2026-10-26 — shared report links and the accountant export

## Added 2026-10-29 — phone alerts (idea 53)

- **A new outbound channel: the browsers' push services.** When something waits for the owner's yes, `lib/push/send.ts` POSTs an encrypted message to the phone's own push service (Google's FCM, Apple's `*.push.apple.com`, Mozilla's, Windows'), which delivers it to the device. It is SYB's own channel to its owner, like Resend, not a business's connected account: no connector, no scope and no execution provider is involved, and `lib/push/no-connector.test.ts` walks the send path's imports and fails on anything under `lib/connectors` but the shared cipher, or anything under `lib/execution`. One request per message, a 10-second timeout, no retry, no redirect followed. A 404 or 410 deletes that subscription; anything else is logged with the account id. The endpoint must be on that host allowlist (`lib/push/endpoints.ts`), checked when it is saved and again before every send, so a stored URL can never point the server anywhere else. The network must reach those hosts (Apple names `https://*.push.apple.com`).
- **What leaves.** The payload is encrypted for the one browser (RFC 8291, aes128gcm, a fresh key and salt each time): the push service sees ciphertext, the request headers and SYB's public VAPID key. The words are fixed per proposal kind ("1 thing waits for your yes: a price change", "3 things wait for your yes") and never a proposal's own title, so no money figure, customer name or contact detail reaches a lock screen or a push service. The notification has no action button. It opens the card, where the yes is given signed in, through the queue's own decision path (rule 12).
- **Subscriptions are secrets (rule 10).** Whoever holds an endpoint and its keys can push to that phone. `push_subscriptions.encrypted_subscription` is the subscription sealed with `encryptSecret` (AES-256-GCM under `CONNECTOR_KEY`), the endpoint is looked up by an HMAC under `stableKey`, and no API returns either. A row is deleted on sign-out from the browser that made it (`revokeSession`, same transaction), on a 404 or 410, from the card, and with its user or account (`ON DELETE CASCADE`). Rotating `CONNECTOR_KEY` makes existing rows unreadable: they are skipped and logged by id, and each phone switches on again.
- **New environment variables.** `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (all three, or phone alerts are off and the card says so). The private key is as secret as `CONNECTOR_KEY`; `npm run vapid:generate` prints a pair and writes it nowhere, and the owner pastes it into Vercel. A pair that doesn't belong together is refused and logged without the key. Replacing the pair means every phone switches on again. `PUSH_SERVICE=fake` (development only, refused in production) records instead of sending.
- **The routes.** `/api/push`: every POST must pass `isSameOriginPost`, every call needs a signed-in session for the account (`matchingSession`), and subscribing refuses a non-push endpoint. `GET /api/proposals/:id` is read-only and returns only the caller's own proposal (a foreign id is a 404). `/api/cron/push-held` takes `CRON_SECRET` like the other crons.
- **Sign-in return.** A sign-in started from a proposal's card comes back to it through a 15-minute httpOnly cookie (`syb_return`) that may only ever hold `/proposals` or `/proposals/<uuid>` (`lib/auth/return-to.ts`), so it can't become an open redirect.

The reviewer's name never reaches the model, and email addresses and phone numbers in the words are masked. SYB never posts a reply: there is no write to any review platform and no new scope. The Google Business Profile API was ruled out because its only scope (`business.manage`) can write (I-45a; decided 2026-11-01 as a write consent used only to read — see below).
- **PII.** The reviewer's public name and the words live on the `reviews` row only: no contact, log line, watch line or summary line holds them. Rows expire 365 days after filing (deleted on filing, on the screen's read and by the weekly cron), and "Remove this review" deletes the row with an `erasure` decision that holds ids and a hash only.

## Added 2026-11-01 — Google Business Profile reviews, a write consent used only to read (I-45a)

Decided by the owner on 2026-11-01: "go ahead with I-45a", then, asked how SYB should hold the permission, "as a write consent".

- **Where the scope lives.** Google's one Business Profile scope, `https://www.googleapis.com/auth/business.manage`, can also reply to reviews and edit the listing. It is NOT in the measurement registry: `SCOPE_REGISTRY` and its rule-9 audit are unchanged, and a test re-asserts that the audit refuses `business.manage`. It is one write scope of a new execution provider, `google_business_reviews`, with **no operations**, so the engine has nothing it could run with it, and its executor refuses every op at preflight and at execution. A new fence in `auditExecutionRegistry`, `FENCED_SCOPES`, fails the build if `business.manage` appears under any other provider, as a readback scope, or beside an operation (planted cases tested).
- **The consent**, like Meta's: the owner types "allow reading reviews" on `/connections`, then Google's own screen asks for exactly that scope (authorization code, `access_type=offline`, `prompt=consent`, PKCE S256 with the verifier derived from the nonce, a signed ten-minute state bound to the account, business and phrase hash, and a single-use httpOnly nonce cookie scoped to `/api/connections/google-business`; no `include_granted_scopes`, so sign-in's scopes don't ride along). The grant's `scope` must match exactly, one more or fewer refused by name, before anything is read with it. The refresh token goes through `connectForExecution`: proven with Google, encrypted at rest with the connection-secret cipher, never returned or logged. A decision-log `consent` row (owner-actored, the person's `user_id`, ref the connection, a hash over the lines shown, the scope, the phrase and the location) is written or the connection is disconnected again. Granting, picking and revoking are `write_access.manage` (owner only); the callback GET is on the role-wiring test's mutating-GET list. Revoke wipes the secret at once; the owner is told how to remove SYB on Google's side too (SYB sends no revoke call, keeping its Google traffic to reads and the token endpoint).
- **The GET-only fence** (`lib/google-business/client.ts`): every request goes through `gbpRequest`, which sends only to an endpoint on `GBP_ENDPOINTS` with that endpoint's method: `GET` accounts list, `GET` locations list, `GET` `accounts/{a}/locations/{l}/reviews`, and `POST` Google's OAuth token endpoint (code exchange and refresh). Paths are anchored, so `…/reviews/{id}/reply` matches nothing; a read may carry no body; redirects are refused. `client.test.ts` fails the build on a changed list, on any off-list request (reply update/delete, listing patch, revoke, http, look-alike hosts — each planted and refused before fetch), on `PUT`/`PATCH`/`DELETE` or a second `POST` anywhere in `lib/google-business` code, on any bare `fetch(` there, and on any file outside it naming a Business Profile API host. `lib/google-business/` is on the rule-21 forbidden list.
- **The read**, on the daily `connector-sync` beat as its own isolated step (a Google failure is logged and reported as null; the sync still reports): at most 4 pages of 50 per business, 200 businesses a run, reviews no older than the retention year, two attempts on 429/5xx, 15 s timeouts. Reviews file through `fileReview` (source `google`, read by `api`), keyed on Google's review name per business, and are checked against the other way in (a forwarded email) under a per-business advisory lock, so the same review files once either way round. Reviews older than a week (the backfill on connecting) file without an alert. Review words stay content (rule 24); the reviewer is only the public name Google shows (none when anonymous), erasable, gone after 365 days. A revoked grant marks the connection failed with a fixed sentence. Log lines hold the account id and counts.
- **Not armed until configured:** the Google client (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, shared with sign-in) and `GOOGLE_BUSINESS_API_APPROVED=true`, set once Google approves SYB's Business Profile API access. Without them the button says it isn't set up yet and the read beat skips. No write happens, so the Session D real-write gate doesn't apply; the consent is recorded exactly as Meta's is.

## Added 2026-10-29 — several businesses, teams and roles (idea 52)

The access model, and how it is held.

- **One account is one business; a person is a `users` row in one account.** One email may now have a row in several accounts (`users_account_email_idx` on account and email replaces the global unique). No row and no session spans two accounts. Every route still takes its account and profile from the session through the one door (`resolveAccess` / `matchingSession` / `currentSession`), so a switch changes everything a screen sees and nothing reads across accounts.
- **Switching** (`POST /api/auth/switch`, same-origin form) opens a new session for the target account's own row, only when that row's email equals the current session's verified email exactly (both stored normalised). A business the person isn't on, or was taken off, is "no such business": existence isn't confirmed. The browser's old session token is retired; no other session is touched. Each switch is an `account_switch` decision-log entry with ids only. A sign-in for an email on several businesses lands on "Which business?" (`/login/choose`), which lists only that email's own businesses by name and role.
- **Invites** (`team_invites`): 32 random bytes in the link, only the sha256 stored (unique), single use (`accepted_at` claimed under a row lock), seven days, revocable; a newer invite to the same address withdraws the older one (a partial unique index allows one open invite per address). **The token is not an identity:** joining needs a sign-in proven for exactly the invited address — a session already signed in as it, or a sign-in link emailed to it from the invite page (the link is sent to the invite's address, never one the request names, and carries the invite id on `login_tokens.invite_id`). A wrong address is refused at both doors and joins nothing. Because the invite link alone can't sign anyone in, it may be shown on screen to copy when email isn't configured.
- **Roles** are one table, `ROLE_ACTIONS` (`lib/auth/role-actions.ts`, re-exported by `lib/auth/roles.ts`): action → least role, tested exhaustively against the plan's lists. `requireRole` is called in every mutating handler: 70 POST/PUT/PATCH/DELETE handlers in 80 route files; 54 check a role, and 16 are listed with a reason in `app/api/role-wiring.test.ts` (sign-in steps, the public widget, signed webhooks, token links, the OPS_KEY panel, leaving the intake). The Meta callback GET, which finishes a write-access consent, is held to the same rule. The structural test fails the build on an unlisted handler without `requireRole`, on an action that isn't in the table, and on a stale allow-list entry. A role is read from the users row on every request, so a change or a removal applies at once.
- **Rule 13 stays the owner's:** connecting, disconnecting and every write-access consent (`connections/execute`, `connections/email`, the Meta login flow, and since I-45a the Google Business Profile flow) need `owner`. So do billing, erasure, imports, the team, hard limits and the business's rules. Chat confirmations ask for the same role as the screen's own route (each catalogue row names its action).
- **At least one owner, held by the database:** the deferred constraint trigger `users_keep_an_owner` (migration 0070) refuses any commit that leaves an account with users but no active owner. It locks the account row (`FOR NO KEY UPDATE`, which foreign-key checks don't wait on), so two owners demoting each other at once serialise and the second fails (tested with two real transactions).
- **Removal** keeps the row (proposals and the log name it), sets `removed_at` and revokes every session in the same transaction, and deletes their phone-alert subscriptions; `currentSession` refuses a removed member.
- **Phone alerts (idea 53) on a team:** a device is its person's own — the list, removal and test send are scoped to the signed-in user — and alerts go only to devices of owners and managers still on the team, since an alert asks for a decision. Switching alerts on needs `alerts.subscribe` (manager); removing your own phone is anyone's.
- **The decision log records who:** a nullable `user_id` on `decision_log` (no foreign key, like `profile_id`) is filled on approvals, declines, change requests, reply and campaign approvals, chat confirmations, report links and every team kind. Team entries hash ids, a role and a time; no email or token is ever logged or hashed.
- **Isolation tests** (`app/api/isolation.test.ts`): structurally, every route under `app/api` goes through the door or is a listed public route with its own credential, and no route chooses its business from a request field (only `auth/switch`, which checks the email). With real requests (the real door, only `next/headers`' cookie jar stood in), business A's session holding B's validly signed cookie opens nothing (profile, team, menu); A can't decide B's proposal, remove, re-role or un-invite B's people, or switch into B; a viewer's approve is a 403 with its reason; a manager approves (logged with their user id) but can't connect; a viewer can stop but not resume; a removed member's session opens nothing.

## Checked and sound

- **Encryption at rest:** AES-256-GCM with a fresh IV every time, and a strict key length.
- **Secrets:** never returned by the API and never logged.
- **SQL:** every query is parameterized; there is no `sql.raw` anywhere.
- **The decision log:** append-only, enforced by database triggers on UPDATE, DELETE and TRUNCATE.
- **The execution engine:**
  - only approved proposals run, and nothing changes after approval;
  - the halt is checked before every attempt;
  - the undo payload comes from the database, never the client.
- **The read-only scope audit:** the build fails on any write scope.
- **The Stripe webhook:** HMAC over the raw body with a constant-time compare and a replay window.
- **The support widget:**
  - all text is rendered with `textContent`;
  - each conversation token reads only its own transcript;
  - the support tier imports no execution, profile-write or connector code (an import-graph test enforces it).
- **Sentry:** `sendDefaultPii: false`, with no request bodies sent.
